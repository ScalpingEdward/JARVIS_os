# JARVIS / AURON — Canonical Master Plan

Status: canonical project roadmap
Repository: `ScalpingEdward/JARVIS_os`

## 1. Mission
JARVIS is the master operating system. AURON is its controlled intelligence/orchestration layer. Vertical capabilities operate through one governed core, one Command Centre, shared identity/audit state, and explicit safety boundaries. Build sequence must be preserved.

## 2. Source-of-truth rule for every new chat/build session
1. Read this file from `main`.
2. Verify the last claimed PR is actually merged into `main`.
3. Inspect current implementation on `main`.
4. Continue from the checkpoint and dependency graph.
5. Never restart merged layers or invent merge state.
6. Reconcile implementation and roadmap explicitly if they disagree.

## 3. Architecture invariants
- JARVIS = master OS; AURON = orchestration/intelligence/governance.
- Command Centre remains operational UI with persistent command/text interaction.
- Consequential external actions require explicit execution boundaries, observable results, audit and failure state.
- Simulation remains independent of external execution.
- Provider adapters cannot bypass central policy/risk/approval controls.
- Idempotency, reconciliation, health, provenance/version state and fail-closed behavior are core infrastructure.
- Secrets never belong in source control.
- External execution is deliberate, never default.

**New capability (2026-08-30) — real, wired Trading Accounts & Strategy Assignment registry:** `backend/app/accounts/` (`models.py`, `service.py`, `api.py`) wired into `main.py` at prefix `/v1/accounts`. This is the first *persistent source of truth* for which accounts AURON manages and which strategies run on each — the foundation the vision needs ("manage prop-firm accounts, run 1-2 strategies per account, and also trade live accounts"). It follows the Research pattern: real sqlite persistence (`data/accounts.db`, gitignored), fail-closed validation, and an append-only `account_audit` trail for every mutation. Capabilities: register `prop`/`live`/`demo` accounts (prop accounts *require* a `PropFirmRules` set: max daily loss %, max total drawdown %, profit target %, min trading days, static/trailing drawdown); `(login, server)` uniqueness; assign strategies with a per-account cap (default 2, honouring the "1-2 strategies per account" rule), no duplicate `strategy_id`, and total allocation ≤ 100%; push broker state snapshots (`balance`/`equity`/`day_start_balance`) that auto-flag `breached` status on a prop rule violation and count distinct UTC trading days; compute live compliance (daily-loss / drawdown / profit headrooms, profit-target progress, breach reasons); and `suspend`/`activate` with breached accounts blocked from re-activation. Endpoints: `POST /v1/accounts`, `GET /v1/accounts`, `GET /v1/accounts/{id}`, `GET|POST /v1/accounts/{id}/strategies`, `DELETE /v1/accounts/{id}/strategies/{strategy_id}`, `POST /v1/accounts/{id}/state`, `GET /v1/accounts/{id}/compliance`, `POST /v1/accounts/{id}/suspend`, `POST /v1/accounts/{id}/activate`. **No order execution** is introduced here — this is deliberately the read/registry foundation; execution reuses the existing gated executor modules in a later PR. Covered by `backend/tests/test_accounts_registry.py` (22 tests: registration rules, uniqueness, strategy caps/allocation, compliance math, daily-loss/drawdown/trailing-drawdown breaches, trading-day counting, suspend/activate, persistence across re-init, and the wired API surface). Full suite green: 4267 passed, 0 failed (4245 + 22 new).

**New capability (2026-08-30) — MT5→Accounts state sync bridge:** `backend/app/account_state_sync/` wired into `main.py` at `/v1/account-state-sync`. Bridges the read-only MT5 bridge (`/v1/mt5`, which stores inbound snapshots from Windows/VPS MT5 terminals) and the persistent accounts registry (`/v1/accounts`). On-demand sync finds each registered account's MT5 terminal by exact `(login, server)` match, extracts the live broker snapshot (`balance`, `equity`), and pushes it into the registry via `POST /v1/accounts/{id}/state` where compliance checks and breach-detection run automatically. Syncs only `active` accounts by default; the `force` flag includes `suspended`/`breached` for manual recovery flows. The `account_ids` filter syncs a specific subset. Real-world flow: Windows/VPS runs `mt5_bridge_client.py` → pushes snapshots to `/v1/mt5/terminals/{id}/snapshot` every 5s → operator or scheduler calls `POST /v1/account-state-sync/sync` → accounts registry sees live broker state and flags breaches without any manual intervention. Endpoints: `GET /v1/account-state-sync/status`, `POST /v1/account-state-sync/sync`. Covered by `backend/tests/test_account_state_sync.py` (18 tests: matching/non-matching terminals, breach detection during sync, filtering by account_ids, force flag, multi-account sync, status tracking, API surface). Full suite green: 4285 passed, 0 failed (4267 + 18 new). This closes the live-observability loop — AURON now sees real broker account states and can auto-detect prop-firm rule breaches.

**New capability (2026-08-30) — Trading strategies infrastructure + scalping_3tp implementation:** `backend/app/strategies/` wired into `main.py` at `/v1/strategies`. This is the **trading brain** — ICT/SMC-based entry logic with multi-TP exits. Each strategy receives a `MarketSnapshot` (current price, HTF bias, Fair Value Gaps, Order Blocks, structure levels, session) and returns either a `TradingSetup` (entry, stop-loss, 3 TPs with partial-close percentages, risk-reward ratio, confidence score, reasoning) or a clear reason why no setup was generated. **Implemented strategies:** `scalping_3tp` — FVG + Order Block mitigation with 3 TPs at 30%/50%/100% RR, min 1:2 RR. Entry logic: Long requires HTF bullish + price mitigating bullish Order Block + bullish FVG; Short requires HTF bearish + price mitigating bearish Order Block + bearish FVG. SL placed below/above Order Block with 0.05% buffer. TPs calculated at 30%, 50%, and 100% of the risk-reward distance. Confidence score starts at 60% and increases 10% per RR point. Setup invalidated if SL is hit (structure break). **Second strategy `ict_silver_bullet`** (added 2026-08-31, `backend/app/strategies/ict_silver_bullet/`): session-gated to London/NY windows, FVG entry aligned with HTF bias, structure-based SL (nearest protective swing, FVG-boundary fallback) and nearest structure-liquidity target with 2 TPs (50%/100%), min 1:2 RR — deliberately uses the `session` + `structure_levels` snapshot fields `scalping_3tp` ignores, covered by `backend/tests/test_strategy_ict_silver_bullet.py` (19 tests). **Future strategies** (`smc`, `open_range`) follow the same pattern and will be added to the registry incrementally. Service layer (`strategies/service.py`) maintains a registry of all strategies with metadata (id, name, description, evaluate function) and provides methods to evaluate a single strategy, all strategies, or filter to only valid setups. Endpoints: `GET /v1/strategies/` (list all), `POST /v1/strategies/evaluate/{strategy_id}` (evaluate one), `POST /v1/strategies/evaluate-all` (evaluate all, including no-setups), `POST /v1/strategies/find-setups` (filter to only valid setups). Covered by `backend/tests/test_strategy_scalping_3tp.py` (15 tests: valid long/short setups, SL placement, TP calculation, confidence scoring, no-setup scenarios for neutral HTF/missing OB/missing FVG/wrong direction/price not mitigating/already mitigated structures, minimum RR enforcement, result model consistency) and `backend/tests/test_strategies_api.py` (16 tests: list strategies, evaluate single strategy with valid long/short/no-setup/unknown strategy/invalid snapshot, evaluate-all including no-setups, find-setups filtering, service layer unit tests). Full suite green: 4316 passed, 0 failed (4285 + 31 new). This is the **first real trading logic** — strategies generate actionable setups with precise entry/SL/TP levels. **No execution yet** — that comes in the next PR where we wire strategy assignments + account compliance + the existing approval-gated MT5 executor.

**New capability (2026-08-31) — Setup Submission bridge (orchestrator output → approval gate):** `backend/app/setup_submission/` (`__init__.py`, `models.py`, `service.py`, `api.py`) wired into `main.py` at `/v1/setup-submission`. This is the **bridge** that turns strategy output into approval requests, connecting the accounts registry (`/v1/accounts`) and the strategies brain (`/v1/strategies`) to the human-in-the-loop approval gate. Flow: `POST /v1/setup-submission/submit` accepts a full `MarketSnapshot` plus an optional `account_ids` filter; for every *executable* account (fail-closed: status must be exactly `active`, so `suspended`/`breached`/`passed` accounts are evaluated but never submit) it evaluates each of the account's *enabled* strategy assignments against the snapshot; every resulting `TradingSetup` becomes a `SubmittedSetup` (account_id, login, strategy_id, symbol, side, entry, SL, TPs, RR, confidence, reasoning) with a freshly generated `approval_request_id` (UUID4). It returns a `SetupSubmissionReport` (symbol, total_accounts_evaluated, total_executable_setups, total_submitted, submitted_setups, optional skipped_reason). **This never executes trades** — it only records pending approval requests for a human operator to resolve through the existing approval-gated execution chain (`auron_demo1_approval_handoff/resolution/…_v21_26x`). Approval requests are held **in memory** keyed by `approval_request_id` for now; a later PR will persist them into the real Phoenix `demo1_approval_inbox` format without changing this module's public contract. Endpoints: `POST /v1/setup-submission/submit`, `GET /v1/setup-submission/pending`, `GET /v1/setup-submission/pending/{approval_request_id}` (404 on unknown). The service's account-registry and strategy-service dependencies are injectable for isolated testing. Covered by `backend/tests/test_setup_submission.py` (18 tests: zero accounts, one account × one/two strategies, multiple accounts, breached/suspended accounts submit nothing, no-setup snapshot, unique approval IDs, account_ids filter, pending list/single/unknown lookup, independent repeat submits, symbol-mismatch rejection, and the wired `/submit` + `/pending` API surface). Full suite green: 4353 passed, 0 failed (4335 + 18 new). **No order execution is introduced here** — the operator still approves/rejects through the existing Phoenix inbox; the next PR wires approved setups into the gated MT5 executor.
